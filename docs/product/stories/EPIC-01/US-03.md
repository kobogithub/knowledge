# US-03: PRD con épicas derivado de un PROJECT.md aprobado

**Épica**: EPIC-01
**Estado**: Borrador — pendiente de revisión
**Firmado por**: —
**Fecha de firma**: —
**Prioridad**: P1
**Rol ejecutor**: Planner (`knowledge-x6e`)

Como PM quiero correr `/product-prd` sobre un `PROJECT.md` aprobado y obtener un
`docs/product/PRD.md` con épicas, roadmap por sprint y riesgos, para tener el contrato de
alcance con el cliente antes de escribir cualquier spec.

## Criterios de aceptación

```gherkin
Feature: PRD derivado del discovery

  Scenario: /product-prd exige PROJECT.md aprobado
    Given docs/product/PROJECT.md con Estado "Borrador"
    When el Planner corre /product-prd
    Then el comando se detiene sin escribir PRD.md
    And informa que PROJECT.md necesita Estado "Aprobado" con firmante y fecha

  Scenario: /product-prd genera el PRD desde un PROJECT.md aprobado
    Given docs/product/PROJECT.md con Estado "Aprobado"
    When el Planner corre /product-prd
    Then se crea docs/product/PRD.md con tabla de épicas (ID, prioridad, sprint, spec, estado)
    And cada épica tiene valor, alcance previsto y rol ejecutor
    And hay un roadmap por sprint y una tabla de riesgos
    And el encabezado tiene Estado "Borrador" y link a PROJECT.md

  Scenario: Cada épica mapea a una carpeta de spec
    Given una épica del PRD que entra a un sprint
    When el Planner corre /speckit-specify para esa épica
    Then la carpeta specs/NNN-nombre/ queda referenciada en la columna Spec de la épica
    And spec.md referencia el ID de la épica en su encabezado

  Scenario: El alcance del PRD es el contrato
    Given un PRD aprobado
    When aparece un requerimiento que no está en ninguna épica
    Then se registra como story nueva para un sprint futuro
    And no se modifica el alcance de las épicas del sprint en curso
```

## Notas / dependencias

- Depende de US-02 (existe PROJECT.md y su plantilla).
- La decisión "épica ↔ spec" se formaliza en ADR-008 como parte de esta story.
